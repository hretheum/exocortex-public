# F1.3. Export the code through an allowlist of paths

[← F1](../F1-public-repo.md)

## Why

Only what has been chosen on purpose should reach the public repository. A list of forbidden paths always misses something; an allowlist by definition lets nothing new in without a decision.

## What to do

1. Write down the allowlist of paths: the engine package, the database schema, general deployment units, examples, tests. Documentation from private research, configuration of the private instance and one-off scripts stay off the list.
2. Write an export script (code in English) that copies only the listed paths into a clean folder.
3. Rewrite the example configurations (project registry, abbreviation dictionary and the like) from scratch with fictional data. Do not edit the private files into shape.
4. Rewrite tests that contain names of people or projects to use fictional names.
5. Run the F0.4 scanner and the F0.6 comparison over the whole export.
6. Run the tests. Commit the result as the first commit of the public repository.

## Done when

The export contains only listed paths, passes the scanner and the private corpus comparison with no matches, the tests pass, and the allowlist is part of the repository so that anyone can see what was published and why.

## Notes

After the export, engine development moves to the public repository. The private repository keeps the private instance configuration and material that cannot be public. This makes the export a one-off, with no need to maintain a one-way code sync. The allowlist stays in the repository as a record of what was moved.
