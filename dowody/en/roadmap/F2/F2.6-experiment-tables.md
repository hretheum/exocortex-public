# F2.6. Experiment tables and the control set lock

[← F2](../F2-lab.md)

## In brief

This task creates a place in the lab database for everything about experiments: what we compare, which jobs wait in the queue and what came out of them. It also adds a safeguard: the final test (the control set) can be read only once for a given hypothesis.

## Why

The lab compares models and settings, and each comparison is many small jobs and their results. Without one shared place for this data, every new experiment would have its own ad hoc records that cannot be put side by side or checked. Exocortex already had such a place, but it fit only one kind of experiment (pulling short claims out of text), so a general version was needed. The second reason is the honesty of the result: if the final test set could be viewed many times, someone could tune the settings to that very set and the result would prove nothing, like a student who knows the exam questions.

## What to do

1. A migration in the lab database with the tables `experiments`, `exp_configs`, `exp_samples`, `exp_jobs`, `exp_results`, `exp_judgments`. Keep from the existing bench the queue in which a job is leased for the time it runs and retried after an error, and the recording of model, provider (local or remote), tokens (the pieces of text a model is billed by), cost and latency. Store results as JSON (a flexible data format) so that a new kind of experiment needs no change to the table layout.
2. `exp_samples` with the sampling seed (a number that lets the same draw be repeated), a checksum of the content (a short fingerprint that reveals any change to the text) and the data class. In the lab the only allowed class is `public`.
3. Control set lock (the control set is the data kept for the final test): a `touched_at` field. A second read of the control set for the same hypothesis version raises an exception, that is, ends in an error.
4. The queue picks jobs grouped by model, so that llama-swap (the program that loads the needed model into memory) does not switch models on every job.
5. A toy experiment (for example counting document lengths) to test the whole path.

## Done when

The toy experiment goes through the queue and records its results. A second read of the control set ends with an exception. A queue test shows that jobs for two models run in two blocks, not alternately.
