# F2.1. Separate database and processes for the lab

[← F2](../F2-lab.md)

> **Status: done** · as of September 30, 2026
>
> The lab runs on the server on its own internal network, which has no route to the private system, to the local network or to the internet. It has its own database and its own entry point for loading documents, which sees only the `dowody` folder of the owner's notes, read-only. The isolation test runs every night at 03:40: six known addresses of the private database refuse the connection, nothing outside the `dowody` folder is visible, and the lab database answers. The same test run outside the lab network reports an open port and visible private folders, so it does detect a failure when there is one.

## In short

This task puts the lab in a separate, walled-off place on the server, with its own database. The lab is meant to see nothing private, and an automatic test checks every night that this holds.

## Why

The same server also runs a private system with personal notes and other private data. The lab is public: everything it produces goes online. If the two shared a database or a network, one mistake in the settings would be enough for a private note to end up in a public result. So the lab gets its own database and its own network, and every night an automatic test tries to reach the private data from inside the lab and is expected to be refused each time.

## What to do

1. A separate database container, `exocortex-lab-db` (a container is an isolated program with its own set of files, and a Quadlet is a file that tells the server how to start it), with its own volume (storage for the data), its own loopback port (an entry reachable only from the same server) and its own role (an account in the database).
2. Separate units that start the lab processes (the API, which is the entry point for loading documents; the scorer, which computes results; the compiler, which builds pages; the publisher, which sends them to the public repository) with their own environment file (settings) that holds no credentials for the private instance.
3. From the vault (the owner's collection of notes in Obsidian), the lab sees only the synchronised `dowody/` folder.
4. Schema migrations (scripts that create the database tables) run on the lab database from the public repository.
5. A test script: from the lab container, try to connect to the private database (every known address and port) and try to read the private vault folder. Both must fail.

## Done when

The lab database runs with the current schema, and the test script ends with two refusals. The script is in the repository and runs every night together with the gate tests.
